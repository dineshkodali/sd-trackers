01 Resolved — full log

Each entry records the original failure, the root cause, the fix, the exact command used to verify it, and the observed result.

BUG-001 · Unauthenticated access to every data endpoint

Critical · Backend · Tests 02.a×8, 02.b, 02.c

Original failure. Every /api/db/* route accepted anonymous requests and executed them with the Supabase service-role key, bypassing Row Level Security. The safeguarding database was readable and writable by anyone who could reach the port.

Root cause. No authentication middleware existed anywhere in server/. Routers were mounted directly after the body parser. Site isolation and role checks lived only in the browser.

Fix
New server/middleware/requireAuth.ts verifies a Supabase token or the signed built-in token, rejects suspended accounts, and attaches req.user. Mounted on /api/db and /api/smtp.
Command
npx playwright test tests/authorization/api-authorization.spec.ts
Result
20/20 passed

02.c goes further than a status check — it proves a seeded record survives an unauthorised delete attempt. 02.m proves legitimate access still works.

BUG-002 · Forgeable session token granted Super Admin

Critical · Authentication · Tests 02.e, 02.f

Original failure. Bearer sm-jwt-x returned a full Super Admin profile. The prefix was the credential.

Root cause. The token was 'sm-jwt-' + base64url(payload) with no signature, and /api/auth/me short-circuited on startsWith('sm-jwt-'). A second, independent backdoor sat in the frontend: AppContext.login granted itself a Super Admin session with a self-minted token whenever the server login errored.

Fix
server/tokenSigner.ts HMAC-signs the token; signature, issuer and expiry are verified with crypto.timingSafeEqual. Lifetime cut from 30 days to 12 hours. The frontend self-grant was removed entirely.
Command
npx playwright test tests/authorization/api-authorization.spec.ts
Result
passed
sm-jwt-FORGED / sm-jwt-x / sm-jwt-default-superadmin   -> 401
payload re-signed with a stolen signature              -> 401
legitimate login                                        -> 200, signed token

Deliberate behaviour change: offline login as the built-in administrator no longer works. It granted full Super Admin from a check that ran only in the browser.

BUG-003 · CORS reflected any origin with credentials

Critical · Backend · Tests SEC.1–SEC.5

Original failure. A request carrying Origin: https://evil.example.com came back with that exact value plus Allow-Credentials: true. Combined with BUG-001, any website a signed-in member of staff visited could act on the database.

Root cause. server/index.ts echoed req.headers.origin straight back, with no allow-list.

Fix
Allow-list built from ALLOWED_ORIGINS, APP_URL, PUBLIC_URL and the host's own advertised addresses, so LAN access is preserved. Un-listed origins get no CORS headers. Vary: Origin added; PATCH removed from Allow-Methods as no PATCH route exists.
Command
npx playwright test tests/authorization/security-headers.spec.ts
Result
13/13 passed

Originally verified only by manual probe. Automated coverage was added during final regression, including a lookalike domain and a null origin.

BUG-004 · A one-click status change destroyed the record

Critical · Data integrity · Test WF.4

Original failure. Archiving a referral, or changing its status from the table, erased the service user's name, references, council and case notes — leaving a blank shell with a new status.

Root cause. PUT /api/db/:entity/:id passed the request body to toDatabaseRow(), which always builds a complete row and defaults anything absent to ''. That was written with .update(), so every unlisted column was blanked. The Edit modal was unaffected — it submits the full record.

Fix
Read the stored row, merge the partial body onto it, then map. Unknown id now returns 404 rather than 500.
Command
npx playwright test tests/workflows tests/crud
Result
WF.4 passes · 9/9 CRUD
UI probe, inline status dropdown:
  PUT {"status":"In progress","updatedAt":"…","lastUpdatedBy":"Stack Master"}
  FIELDS DESTROYED BY A SINGLE STATUS CHANGE: none

Residual risk: read-modify-write has a small race window — under simultaneous edits the last write still wins.

BUG-005 · Password-recovery endpoint returned 404

High · Authentication · Tests 21.13, 21.15, 21.16

Root cause. The route registration sat inside the catch block of the /me handler, so it only ran if token verification threw during a request. It was never registered at startup, and the entire recovery-link flow was dead.

Fix
Registration lifted to module scope in server/routes/auth.ts.
Command
npx playwright test tests/api
Result

BUG-006 / 007 / 008 / 022 · Unauthenticated administrative endpoints

High · Authentication · Tests 02.d, 02.i, 02.j, 02.k, 02.l

Root cause. /auth/signup, /auth/admin/update-password, /db/migrate and /db/ensure performed no checks. Signup took role from the request body, so an anonymous caller could create a confirmed Super Admin. The staff directory and password history were readable by anyone.

BUG-011 · Background sync running at ~18× the intended rate

High · Application shell · Tests PERF.1, PERF.2

Root cause. The scheduling effect depended on a callback that closed over sites and users; the sync replaced both, so the callback identity changed every run, the effect re-ran, and its 1500 ms initial timer re-armed. The 45 s interval was never reached.

Fix
The sync function is held in a ref; the scheduling effect is mount-only.

100-second instrumented measurement
Result

The application now reaches network idle, which also lifts the standing ban on waitForLoadState('networkidle') in test authoring.

BUG-012 · Compliance forms fabricated records

High · Laundry & Hot Meals · Tests 10.d, 11.d

Root cause — two independent causes. The forms opened pre-filled (115 sent / 115 returned, plus a written food-safety attestation), so nothing was invalid and one click filed a complete record. Separately, schemaAdapter.ts invented values server-side: temperature_c: 65.0, quality_check: 'Passed', vendor and staff names. Its read path repeated this with Number(x || fallback), which also turned a genuine stored 0 into 1, and an unrecorded or genuinely 0 °C reading into a compliant 65 °C.

Fix
Attested fields start empty. numberOrNull() applied on both read and write paths, so unrecorded stays NULL and a real 0 survives. No migration needed — all affected columns were already nullable.
Command
npx playwright test tests/modules/operations.spec.ts tests/validation
Result
24/24 + 53/54 (the remaining one is a known pin)

Expect a visible change: the dashboard's food-temperature compliance figure will now read lower, because unrecorded temperatures no longer count as compliant. That is a correction, but it will look like a regression to anyone watching the number.

BUG-025 · API silently truncated every read at 1000 rows

High · Backend · Test 21.14

Fix

REG-001 · The authentication lockdown broke all frontend data loading

High · Self-inflicted · Tests WF.1, WF.3 and 32 others

The full suite immediately after BUG-001 landed came back 34 failed / 304 passed — worse than before the work started.

Root cause. src/services/apiService.ts sent no Authorization header on reads. fetchEntityRecords, getDbStatus, runMigration and the SMTP calls all used a bare fetch(url). 02 Outstanding — with remediation detail

Nine items. One is a release blocker on its own; the rest are ordered by the harm they permit.

BUG-009 · No rate limiting or account lockout on login

High · Release blocker · Not started

Evidence. Twelve rapid failed logins for one address returned twelve plain 401s with no delay, throttle or lockout. Credential-stuffing and brute force against staff accounts are unimpeded.

Why it blocks release. It is the last remaining High-severity defect, and it undermines the authentication work now in place: strong token verification does not help if a password can be guessed at unlimited speed.

Remediation

  1. Add a small in-memory limiter keyed on both client IP and submitted email, so one attacker cannot rotate addresses and one victim cannot be locked out by a third party's traffic.
  2. Apply to POST /api/auth/login, /auth/reset-password and /auth/admin/update-password. Suggested budget: 10 attempts per 15 minutes per key, with exponential backoff on repeat offenders.
  3. Return 429 with a Retry-After header. Do not reveal whether the account exists.
  4. Mount before the route handlers in server/index.ts, and exempt nothing.
  5. Behind a proxy the limiter must read the client IP from req.ip with trust proxy already set — it is.

Verification. A test issuing 15 rapid failed logins should observe 401 then 429, and a legitimate login from a clean key must still succeed. Add to tests/authorization/.

A dependency-free implementation is fine at this scale; a shared store (Redis) becomes necessary only when running more than one instance.

BUG-026 · Audit trail double-writes, and one copy has no entity link

New · Compliance integrity · Test 20.2 left failing as evidence

Root cause. addAuditEntry dispatches two writes per action: saveEntityRecord('audit', newEntry) and recordAuditTrail(...). The first sends targetItem, which has no matching column; the generic adapter maps it to target_item, the column whitelist drops it, and the row persists with entity_id = null. The second sends entityId correctly.

ActionRowsMissing entity link
CREATE130546 (4%)
DELETE11798 (1%)
UPDATE729 (13%)
SETTINGS_UPDATE11529 (25%)
ARCHIVE82 (25%)

Impact. Two defects in one. Every operator action produces two rows, inflating the trail and making it hard to read; and a consistent fraction of entries cannot be tied to the record they describe. In a safeguarding system the audit trail is the record of who did what, so an entry without a subject is weakened evidence.

Remediation

  1. Remove one of the two dispatches in addAuditEntry — recordAuditTrail is the correct one to keep, as it populates entityId.
  2. Add an audit_trails case to toDatabaseRow mapping targetItem onto entity_id, so the link cannot be silently dropped by the generic path.
  3. Consider a backfill decision for the ~94 existing unlinked rows: they cannot be reconstructed, so they should probably be left and the gap documented.

Verification. npx playwright test tests/workflows/audit-trail.spec.ts — 20.2 should pass, and a new assertion should confirm exactly one audit row per action.

20.2 is deliberately left red. It asserts that a create produces an audit row naming the record — correct behaviour the application does not reliably deliver. Making it pass would mean asserting the broken behaviour.

API-13 · /api/config/* is entirely unauthenticated

Medium · Information disclosure · Verified, not applied

GET /api/config/status returns the environment name, SMTP host, partially-masked SMTP user and every internal LAN IP of the host to anonymous callers. /config/test-supabase and /config/test-smtp let anyone trigger outbound connections from the server.

Remediation

  1. Mount the config router behind requireAuth in server/index.ts, exactly as /api/db is.
  2. Consider requireRole('Super Admin','Admin') for the two test endpoints, which cause the server to make outbound connections.
  3. Remove networkIps from the response, or gate it — it has no client use beyond diagnostics.

Safety already confirmed: getConfigStatus and testSupabase are called only from SupabaseBackendCard in the Settings view, which is post-login and admin-only. Gating will not break the login screen.

Not applied because it would mean changing production code after the verification run without re-running the full suite.

API-14 · /api/db/sync/push has authentication but no role check

Medium · Authorization

Any authenticated user — including Staff — can bulk-upsert twelve tables in a single request. There is no per-record validation, no transaction, and no size ceiling beyond the 15 MB body limit, so a partial failure leaves some tables written and others not.

Remediation

  1. Add requireRole('Super Admin','Admin') to the route in server/routes/db.ts.
  2. Validate each record against the entity's schema before upserting, rather than trusting the array.
  3. Report per-entity success/failure as a status, not a free-text string, so a partial write is machine-detectable.

API-15 · Any authenticated user can enumerate the full staff directory

Medium · Authorization

GET /api/auth/users requires a session but no role, returning every user's email, name, role, site assignments and last sign-in. Both this and /auth/password-audit-logs also mask errors as an empty 200, so a failure is indistinguishable from an empty result.

Remediation

  1. Decide the intended audience. The frontend calls this during sync for all roles, so gating it to admin will need the non-admin sync path adjusting first — do not simply add requireRole without checking that.
  2. At minimum, reduce the payload for non-admin callers to what the UI actually needs (id and display name), withholding email, role and site.
  3. Return real error statuses instead of an empty 200.

LOG-001 / LOG-002 · Residual logging concerns

Low–Medium · Privacy

No passwords or tokens are logged. Two residuals remain:

  • server/routes/auth.ts:466 logs a user's email address during password reset — personal data in server logs, in a safeguarding context.
  • src/utils/diagnosticLogger.ts:124 retains a token's first 16 and last 8 characters. For the signed token the tail is part of the HMAC signature. Eight characters of a 43-character signature is not forgeable, but it is unnecessary exposure in a log the UI can export.

Remediation

  1. Log a stable user id, or a hash, instead of the email.
  2. Redact to the prefix only: drop + token.substring(token.length - 8).

BUG-015 · Proof Documents cannot accept a document

Medium · Blocked on a product decision · Test 13.b failing

The "Upload Compliance Document" form contains no file input. Its seven controls capture metadata only, while the button reads "Confirm & Upload". The module records that evidence exists without ever storing it. Referrals does expose a file input, so this is an inconsistency rather than a platform limitation.

This needs a decision, not a fix

Either implement genuine upload and persistence — reusing the existing AttachmentsSection component and adding an attachment field to DocumentRecord — or relabel the module and its button to reflect that it is a metadata register. Both are legitimate; the choice is yours, and I have not guessed at it.

13.b is left failing so the gap stays visible rather than being quietly accepted.

Untested change · Batch retention

Medium · Coverage gap

D-9 corrected retention to use date / defectStatus / action. The type-checker proved the old code matched nothing and the new field names are correct — but no automated test exercises this feature at all. A token smoke test would not catch a real fault here, so the gap is named rather than papered over.

Remediation

  1. Seed maintenance records either side of a cutoff date, with mixed defectStatus and action values.
  2. Assert the Settings preview counts match, then that archive moves exactly the previewed set.
  3. Assert "only archived" excludes records that are neither Completed nor Closed.

03 Recommended order

  1. BUG-009 — the only remaining release blocker.
  2. BUG-026 — the audit trail is compliance evidence; it should not be doubled or unlinked.
  3. API-13, API-14 — both small, and API-13's safety is already proven.
  4. LOG-001 / LOG-002 — two-line changes.
  5. BUG-015 — needs your product decision before any work starts.
  6. Batch-retention coverage, then the Medium/Low backlog.
  7. Re-run the full suite for a clean release baseline before shipping.
