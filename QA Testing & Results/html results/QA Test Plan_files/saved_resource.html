01 This is not a sales CRM

No Customers, Leads, Contacts, Companies, Deals, Tasks, Activities, Notes or Teams exist here. Exploration confirmed none of those modules are present. Tests written against them would target nothing.

SafeHaven is a UK safeguarding and accommodation-compliance platform for vulnerable people placed in contracted hotels. The customer analogue is a Service User; the account analogue is a Property.

07 Test data & teardown

There is no test database. Every run touches the shared Supabase project holding real safeguarding records.

  1. Prefix all created data QA-TEST-<runId> so residue is greppable.
  2. Tear down in afterEach via the API, not the UI — UI delete depends on the row still being visible, which the archive flow can break.
  3. Never delete pre-existing rows. Baseline before a run and diff after.
  4. Audit rows are unavoidable — every login writes two. Never assert on absolute audit counts.
  5. Seed at least three records per module before sorting or pagination suites; most tables are empty and those assertions are meaningless at n≤1.

Two rules in every spec. Never use waitForLoadState('networkidle') — it cannot resolve while BLK-02 stands. And locate row actions by their title attribute until testids exist.

09 Execution order

  1. Install @types/react. One command, and it immediately exposes real type bugs the current lint hides.
  2. Author the harness, then TS-01 and TS-21. Cheapest and highest signal — catches DEF-01, DEF-02 and DEF-03 straight away.
  3. Build TS-05 Referrals end-to-end as the reference module, then generalise the page object.
  4. Roll the CRUD matrix across the remaining modules.
  5. Add TS-17 mechanics once seeding exists.
  6. Finish with TS-02 RBAC — it needs multiple accounts or role-switch fixtures.

DEF-01 through DEF-05 should be fixed before this suite becomes a release gate. Four of them make a green run misleading: an unauthenticated data API, a forgeable admin token, a dead password-reset route, and a dropdown that cannot express the value driving safeguarding alerts.

Compiled from live exploration of the running application — login, all 21 modules, every create form, and a full create → confirm → search → duplicate → edit → delete lifecycle. All test data was removed; pre-existing records were left untouched.
