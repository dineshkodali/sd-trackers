The 16 “defect pins” are test.fail() tests that reproduce previously known defects. They count as passes while the bug exists and turn into hard failures the moment it is fixed.

01 The finding that matters most

Archiving or editing a safeguarding record destroys its contents. A partial PUT — exactly what the Archive button and the inline status dropdown send — rebuilds the entire database row from the incomplete payload, overwriting every field the request did not mention with an empty string.

The record survives with its new status and nothing else: no service user name, no Port reference, no council, no notes.

Reproduced twice, independently. First by a UI archive action during the suite, then by this controlled probe:

CREATE  -> suName="QA-PROBE-PARTIAL" portRef="PORT-PROBE" council="Camden Council"
           notes="Original notes" officer="Jane Doe" status="Open"

PUT /api/db/referrals/<id>  body: {"status":"Archived","updatedAt":"..."}   → 200 OK

AFTER   -> suName=""  portRef=""  council=""
           notes=""   officer=""  status="Archived"

Root cause. PUT /api/db/:entity/:id calls toDatabaseRow(), which constructs a complete row from whatever it is given and defaults every absent field to ''. The result is passed to .update(), so absent fields are written as blanks rather than left alone.

Blast radius. Three UI paths send partial payloads: the row Archive action, the inline status dropdown in the table, and the Edit modal — which exposes only 11 of the referral's fields, so saving an edit blanks everything it does not show. This is live safeguarding data about vulnerable people.

02 Product defects found by the run

Six distinct defects, accounting for nine of the seventeen failures. None were known before this run.

F-01 · Partial update destroys record contents

Backend / data integrity · Critical · 1 failure (WF.4)

Detailed above. The test failed because the record's identifying tag had been wiped, so the assertion could no longer find it — the record still existed, blank.

F-02 · Compliance forms ship pre-filled with fabricated data

Validation / frontend · High · 4 failures

The Laundry and Hot Meals create forms open fully populated. Every required field already holds a value, so there are zero invalid controls and a single click on “Add Log Record” writes a complete, official-looking operational record that nobody entered.

Property / Hotel *          "Brit Hotel"
Date From *                 "2026-08-31"
Date To (Max 7 Days) *      "2026-09-06"
Dirty Laundry Sent (pcs) *  "115"
Clean Laundry Returned *    "115"
Remarks / Actions Taken     "Batch verified upon ar…"
Logged / Audited By         "Stack Master"

The run created four junk laundry logs and one food log this way, each asserting that 115 items were sent and returned. In a system whose purpose is auditable compliance evidence, a form that manufactures records on one click is a serious integrity problem.

F-03 · A reversed reporting period is accepted

Validation · Medium · 1 failure

Setting the laundry period end date before its start date submits successfully and closes the modal. The Zod schema defines an endDate >= startDate rule, but no view calls the validator, so the rule never runs.

F-04 · Fields marked mandatory are not enforced

Validation · Medium · 1 failure

The Maintenance defect form marks seven labels with an asterisk but sets the required attribute on only four. Three fields presented to staff as mandatory can be skipped: Priority Category * (both controls) and Property Site *.

F-05 · Proof Documents cannot accept a document

Frontend · Medium · 1 failure

“Upload Compliance Document” contains no file input. Its seven controls capture metadata only — title, resident, reference, site, category, confidentiality, file format — and the button reads “Confirm & Upload”. The module records that evidence exists without ever storing it. Other modules (Referrals) do expose a file input, so this is an inconsistency rather than a platform limitation.

F-06 · The RBAC matrix omits the Site Manager role

Authorization · Medium · 1 failure

The Roles view configures “5 Operational Roles” and does not list Site Manager — yet Site Manager is offered in the Add User form, is present in the user validation schema, and is branched on explicitly in the permission logic. Users can be assigned a role whose permissions cannot be configured or reviewed.

03 Why the RBAC suite could not run

Five failures share one cause, and it is not a test defect in the ordinary sense — the application makes the behaviour untestable.

The RBAC specs seed a session with a reduced role and assert the UI withholds privileged controls. All five failed because the app silently restored Super Admin:

seeded localStorage role      : "Staff"
GET /api/auth/me   →  200     : {"role":"Super Admin", ...}
localStorage role after boot  : "Super Admin"
header displays               : Super Admin

/api/auth/me returns Super Admin for any token beginning sm-jwt-, ignoring the stored profile entirely. This is the same backdoor recorded as DEF-02, seen from a new angle: the role attached to that token cannot be reduced. Any holder of a forged prefix string is Super Admin, and no lesser role can be simulated through it.

The fix on the test side is to stub /api/auth/me per role, or to use real per-role accounts. Both are legitimate; neither weakens an assertion. The underlying authorization flaw stands regardless.

07 What to fix first

  1. F-01, the partial-update wipe. It silently destroys safeguarding records through everyday actions — archive, status change, edit. Nothing else on this list competes.
  2. DEF-01 and DEF-02. An unauthenticated data API and a forgeable admin token, on a database of vulnerable people's records.
  3. F-02, the self-filling compliance forms. They manufacture audit evidence on one click.
  4. DEF-03, then the validation gaps F-03 and F-04, then F-05 and F-06.

Once F-01 and the authorization defects are closed, remove the corresponding test.fail() annotations — the suite will then hold the line on all of them.
