01 Security posture

There is no authentication or authorization middleware anywhere in the backend. No guard function, no route wrapper, no role check. A search across server/ for any auth middleware returns nothing.

The single endpoint that inspects a token is GET /api/auth/me — and it grants full Super Admin to any bearer string starting sm-jwt-, with no signature verification.

No PATCH route exists, although PATCH is advertised in the CORS Allow-Methods header. A PATCH to a real entity falls through to the SPA catch-all and returns 404 with an HTML body.

The PUT /api/db/:entity/:id behaviour is defect F-01 from the failure report: the Archive action and the inline status dropdown both send partial payloads, and both erase every field they omit.

05 Endpoint categories

Authentication endpoints — 8

/auth/status, /auth/login, /auth/logout, /auth/signup, /auth/me, /auth/reset-password, /auth/admin/update-password, and /auth/update-password (unreachable). Only /auth/me reads a credential; none of the others require one, including the two that change passwords and create accounts.

Search, filter, pagination and sorting endpoints — none

The API has no query capability whatsoever. Every one of these was ignored, each returning the complete 16-row table:

?limit=1              -> 16 rows   ?search=Brit          -> 16 rows
?page=1&pageSize=1    -> 16 rows   ?site=Brit%20Hotel    -> 16 rows
?offset=5             -> 16 rows   ?status=Active        -> 16 rows
?order=name&sort=asc  -> 16 rows   ?filter[city]=London  -> 16 rows

GET /api/db/:entity issues a bare select('*') and returns the whole table. All searching, filtering, sorting and pagination happen in the browser after the entire dataset has been transferred. That is workable at 16 sites and 6 profiles; it does not survive real caseload volumes, and it means every client holds a full copy of the safeguarding database in memory.

Bulk endpoints — 1

POST /api/db/sync/push accepts twelve named arrays and upserts each into its table. It validates only that each value is a non-empty array — no per-record validation, no size ceiling beyond the 15 MB body limit, no transaction, and no authentication. A partial failure leaves some tables written and others not; the response reports per-entity strings rather than a status.

There is no bulk delete, bulk update or batch-operation endpoint. The application's “batch retention” feature is implemented entirely client-side and issues individual requests.

Orphan endpoints

Three endpoints are defined on the server but never called by the application: GET /api/config/test-smtp, GET /api/smtp/status and POST /api/db/ensure. The last is the more notable — an unauthenticated, uncalled route that replays the entire schema file against the live database.

Highest-value additions

/auth/signup and /auth/admin/update-password should be covered first: both are unauthenticated account-control operations, and a test asserting they reject anonymous callers would pin the most dangerous gap in the surface.
